# ADR 0001: Transaction Boundaries and Session Management

## Status
Accepted

## Context
In our FastAPI application, we use SQLAlchemy as our ORM with asynchronous execution (`AsyncSession`). A common architectural challenge is deciding which layer controls transaction boundaries (i.e., `commit` and `rollback` operations).

If repositories perform `commit` operations:
1. It becomes impossible to run multiple repository calls under a single atomic transaction from the service layer (composite operations).
2. Failures in subsequent steps of a business transaction would leave the database in an inconsistent, partially updated state.
3. Transactional management becomes scattered across data-access logic.

Conversely, if the controller (router) layer manages commits, business logic in the services cannot easily control custom error responses or run operations that require immediate ID generation/flushing without closing the transaction prematurely.

## Decision
We enforce a strict separation of concerns for database transaction boundaries:

1. **Repositories do not commit**: All methods in repositories (inheriting from [BaseRepository](file:///C:/Proyectos/Api-AgricultureHandling/src/repositories/base_repository.py)) must only call `await self.db.flush()`. They must never call `.commit()` or `.rollback()`. This ensures that any data modified is sent to the database but remains uncommitted, allowing it to be rolled back if any subsequent step fails.
2. **Services control transactions**: Business services (inheriting from [BaseService](file:///C:/Proyectos/Api-AgricultureHandling/src/services/base_service.py)) act as the orchestrators. They control transaction boundaries. Any write operation must wrap repository calls inside a `try/except` block, committing the transaction on success, performing a rollback on failure, and refreshing the entity to populate autogenerated fields:
   ```python
   try:
       item = await self.repository.create(data)
       await self.db.commit()
       await self.db.refresh(item)
       return item
   except DatabaseError as e:
       await self.db.rollback()
       raise HTTPException(status_code=500, detail=str(e)) from e
   except Exception as e:
       await self.db.rollback()
       raise e
   ```
3. **FastAPI Dependency Injection**: The database session (`AsyncSession`) is managed by dependency injection (`get_db`) and shared between repositories and services instantiated during a single request lifecycle, ensuring they operate on the same transaction space.

## Consequences

### Positive
* **Atomicity**: Multiple repository operations executed within a service method can be committed or rolled back as a single unit of work.
* **Separation of Concerns**: Repositories focus strictly on mapping data and querying/updating tables, while services focus on orchestrating business rules and transactional boundaries.
* **Consistency**: Standardized error handling and rollback flow throughout all service methods.

### Negative
* **Service Verbosity**: Service write operations require `try/except/rollback` boilerplate. However, this is abstracted cleanly by [BaseService](file:///C:/Proyectos/Api-AgricultureHandling/src/services/base_service.py).
